## P2 — robustness and performance

- **MCP refusals are recognised by their text.** `mcp/src/server.ts` sets `isError: true` when a tool's answer matches `/^Error[: ]/` (v1.40.0), so a new handler that words a refusal differently, or a successful answer that starts with `Error`, is misclassified. Move the handlers to typed results (`{ text, isError }`) so each says what it is.
- **The audit actor is a client-supplied header for API-key callers.** After API-key authentication the actor is `Tailscale-User-Login` as the request carries it (`src/routes/request-context.ts`, `src/routes/storage.ts` and `src/routes/feedback.ts`, each falling back to `api-key`), so any key holder can name another actor in the audit trail. The dashboard's nginx sets the header itself; other clients are not checked. Decide whether API-key callers may set it (pre-existing).

## P3 — tidy-ups

- **Turn on `noUncheckedIndexedAccess` in the root (Worker) `tsconfig.json`.** With it, `pnpm exec tsc --noEmit -p . --noUncheckedIndexedAccess` reports 122 errors across 31 files under `src/` (most in `src/audit/cf-audit-poll.ts`, `src/routes/admin.ts`, `src/queue/r2-events.ts` and `src/routes/storage.ts`). One is in `src/utils/credential-redaction.ts`, a vendored file pinned by hash in `credential-redaction.json`: a vendored, hash-pinned file must change upstream first, then be re-vendored with its new digest, before the flag can be enabled.
- **The routing benchmark's baselines are all 1.0 with a 1.15 limit**, while measured medians reach about 1.07–1.09 under load (`scripts/check-routing-benchmark.mjs`), so headroom is small. Consider per-benchmark baselines measured on an idle machine, or the median of five runs.
- **nginx clears only the named internal headers.** The `/api` proxy clears `X-Bifrost-Dashboard` and sets the key and identity headers by name; another `X-Bifrost-*` header a client sends still reaches the Worker, which never trusts them. Clearing every one would need an nginx module or an allowlist map of forwarded headers.
- **The dashboard script check covers `<script>` elements only.** `scripts/check-dashboard-security.test.mjs` does not reject inline event-handler attributes (`on*`) or `javascript:` URLs on other elements, and it reads the source `admin/index.html`, not the built `admin/dist/index.html`. The CSP (`script-src 'self'`, no `'unsafe-inline'`) blocks both at runtime; sweeping every element's attributes and checking the build output would make the test match its name.
- **The dashboard names a fixed external font host.** `admin/index.html` preloads its font from one host and the nginx CSP `font-src` allows it. Make the host configurable alongside the other deployment settings, or self-host the font, so the template carries no deployment-specific host.
- **The dashboard build strips HTML comments with a regular expression.** `admin/src/lib/strip-html-comments.ts` matches `<!--…-->`, which misses comments that end with `--!>` and the `<!-->` form, the same class as the v1.40.1 CodeQL alert. Strip comments with `parse5` (already a root devDependency) as the file's own limitation note suggests. Also have `scripts/check-dashboard-security.test.mjs` parse each input once (it parses twice per call today).
- **One shared after-answer helper for every audit site.** The route, storage and feedback handlers (`src/routes/admin.ts`, `src/routes/storage.ts`, `src/routes/feedback.ts`, and the Worker's own `waitUntil` sites in `src/index.ts`) each call `c.executionCtx.waitUntil(…)` inside `try`/`catch` and skip the work when there is no execution context (a test calling the app without one), while the QR handlers run theirs inline through a QR-local `afterAnswer` (`src/routes/qr.ts`, v1.41.0). Move a waitUntil-or-inline helper to a shared module and use it at every site, so every audit behaves the same; production always has a context, so only tests see the difference.
- **The QR listing reads recent codes even when its filters will drop them.** `listQRs` (`src/kv/qr.ts`) runs the D1 recent read and one KV `get` per recent id it lacks on every listing, also when the type, tag or search filter will then drop every merged code. Cheap at QR volumes (at most 100 rows, usually none); filtering on the row before the KV read is not possible (a row holds only the id and incarnation), but a search that cannot match a recent id, or a type or tag filter, could skip the reads whose records it would drop.
- **The public sanitisation check crashes on an unstaged deletion.** `scripts/check-public-sanitization.mjs` reads every tracked file, so a file deleted in the working tree but not yet staged makes it fail with `ENOENT` instead of being skipped. Skip tracked paths that no longer exist (the commit will drop them).

### v1.41.2 residuals

- **QR writes still read a 2xx without a record as a refusal.** QR create and update (`admin/src/lib/api-client.ts`) throw `ApiError(400)` when the Worker answers 2xx with `success: false` or no data, so the QR page treats an answer that may have landed as a definite refusal and does not mark its retry for the read-back (`uncertainCreate`). Route writes use `UNCONFIRMED_ANSWER_STATUS` (0) for the same case since v1.41.2 (`confirmRouteWrite`); using it for QR would make such a save "could not be confirmed" and mark its retry.
- **A request blocked before reaching the Worker is classed uncertain, and dropping it discards an earlier own answer.** `isUncertainAnswer` cannot tell a request that never left the browser from one whose answer was lost: a fetch rejected before it was sent (a `TypeError`, as for a dropped connection) reads as a write that may have landed, so the store drops its entries for every key the write held and the Routes page says "Could not confirm the …". Dropping a failed write's held entries is not free: it also discards an EARLIER confirmed own answer at that key (a save answered a minute ago, then a second save that never got out), so while KV lags the refetch can show an older row than that answer; an edit opened from it then sends the older `updatedAt` and meets a 409, which heals it (the dialog closes and the reopen reads the refetched route). Telling "never sent" apart would keep those entries for the rest of their 90 s.
- **An uncertain create or edit closes its dialog, and the Routes page create is not marked for the read-back.** The Routes page closes a create, edit, migration or transfer dialog on any answer that is not definite (`onWriteFailure` in `admin/src/pages/routes.tsx`), so what the operator typed is lost even when the request never left the browser (an offline `TypeError`, which `isUncertainAnswer` cannot tell from a lost answer): they type it again. And the page's create does not pass `afterUncertainAnswer` (`useCreateRoute`; the QR page marks its retry, `uncertainCreate`), so a retyped retry of a create that did land meets 409 "Route already exists" instead of reading the route back and adopting it. Keeping the dialog's input for a reopen after an uncertain answer, and marking the Routes page's retry as the QR page does, would close both.
- **The store exposes live and snapshot views side by side.** `pendingRoutes.isPending`, `pendingRoutes.project` and `projectRows` read the store's state NOW, while `getSnapshot()` and `getAdmissionSnapshot()` give the frozen views a render subscribed to. The Routes page reads the live state only at click or submit time (`refuseIfHeld` reads `getAdmissionSnapshot()` there; the dialogs read `answerAt` and `generation`); a caller that read a live one during render would bypass the frozen snapshot and could tear (two rows of one render answering for different versions). Exposing the live readers only to event handlers (or not at all) would close it.

### v1.41.1 residuals

- **The route cache is best effort, by design.** `admin/src/lib/route-pending.ts` shows this session's own write answers for 90 s whatever the listings say: another writer's change to the same route within those 90 s is masked by this session's answer until the server refuses the stale `expectedUpdatedAt` with a 409, which forgets the entry when it is the very version the request expected (the table toggle sends no precondition, so a toggle does not heal it; the next edit does). An entry that expires stays shown until the refetch it triggers (the expiry runs 5 s after the first entry comes due and takes every entry due by then, so each is held 90 to 95 s and a burst shares one refetch, v1.41.2) has refreshed every ACTIVE route query, retried every 30 s until it has, so what shows after the 90 s is that refetch's result, which still shows the lagging row when KV lags beyond the 90 s. Inactive route queries (no enabled observer) are removed at expiry instead of refetched, so one mounted again loads anew; a query whose observers are all disabled (the QR editor's route picker while the code is unlinked) is inactive too, so it is removed while its observer stays mounted; on its next render the observer builds an empty query in its place (TanStack Query's `setOptions`), shows no rows while disabled, and loads anew once enabled. A created, migrated or transferred route appears in a listing only on the refetch (no page gains a row), and a saved answer keeps its listing position (only a search it no longer matches, or a by-target object it no longer serves, drops it). A 404 only refetches (the Worker's `Route not found` carries no code, like an unknown endpoint's 404), so a route deleted elsewhere can still show this session's answer for up to 90 s while a listing lags; a route-specific 404 code from the Worker would let the store mark it gone.
- **Expiry's reach and its count (v1.41.1 review).** (1) The other domains' prefetches (`usePrefetchAllDomainRoutes`) have no observer, so expiry removes them, and the Routes page's cross-domain duplicate-target note (`allDomainRoutes`, read with `getQueryData`) lacks those domains until the page prefetches again (a domain change or a remount); observing the prefetches (`useQueries`) would keep them active, refetched and counted. (2) A WATCHED route query whose refetch keeps failing (an error answer, not only offline: Storage's by-target answer for an object whose listing errors) keeps the whole batch shown, retried every 30 s, for as long as it fails. (3) The refresh is decided by count (`routeQueriesRefreshed`, v1.41.2): a query is refreshed when no fetch was in flight at the mark, it has no error, and its data was written at least once since. A query already fetching when the expiry began counts as not refreshed (the expiry's refetch joins that fetch, `cancelRefetch: false`, so its data is written once, by that fetch's answer, and a count cannot tell whether that answer was sent before the write landed in KV), costing one more refetch 30 s later; a route query that were always fetching would never let a batch drop (none polls today).
- **A projected total counts only the rows hidden on the page shown (v1.41.1 review).** `project` lowers `total` by the rows it hid from the listing it is given (min 0) and leaves `offset` and `hasMore` the server's, so an own delete of a route listed on another page leaves this page's total one high, and the next page's offset still counts the hidden row, until the refetch.
- **The QR editor's uncertain mark holds one route.** `uncertainRoute` keeps only the last create that got no certain answer (keyed with `keyOfInput` since v1.41.1), so an uncertain create at `/a`, then one at `/b`, then a retry at `/a` is not marked: its "Route already exists" fails instead of linking the route the first create made. A set of uncertain keys would close it.
- **A route write that never settles holds its routes.** The store frees a write's routes in `onSettled`, and the dashboard's fetches have no timeout, so a request that never answers keeps every route it holds refusing other writes ("Another change to this route is still saving") until the page is reloaded. Likewise an expiry refetch that never settles keeps its batch of entries shown (the store drops a batch only once its refetch has refreshed every active route query; since v1.41.2 it joins a listing fetch already in flight rather than cancelling it, so a listing fetch that never answers holds every later batch too), and one that keeps failing (offline, or an error answer to a watched query) keeps it shown, retried every 30 s, for as long as it fails. A request timeout in `fetchApi` would bound the first two.
- **One `withAdmission` helper for the five route mutation factories.** `createRouteMutationOptions`, `saveRouteMutationOptions` (update and toggle), `deleteRouteMutationOptions`, `migrateRouteMutationOptions` and `transferRouteMutationOptions` (`admin/src/hooks/use-routes.ts`) each repeat the same `onMutate` (acquire), `onError` (`settleFailure`) and `onSettled` (release) wiring around their own request and answer. One helper taking the request, the keys, the answer to record and the refused version would leave each factory only what differs (deferred from the v1.41.1 review).
- **A legacy readable route whose stored path does not round-trip cannot be managed through ordinary writes.** The store keys a listed row by its stored path as is, and a write's request by its path normalised once, as the Worker does (v1.41.1 review). For a readable record whose stored path holds `?`, `#` or a `%` surviving one decode (`/p?x`, as `/p%3Fx` would be stored), every ordinary write REFUSES the path rather than normalising it to another key (`/p`) and writing there: an update or toggle (`UpdateRouteSchema`'s `RoutePathSchema` in `src/routes/admin.ts`: a 400, or first a 404 or 409 from the pre-read), a transfer, a migration from it, and since v1.41.2 the ordinary delete (400; it resolved `/p?x` to `/p` and deleted that live route, now closed). Only the recovery delete (`recover=invalid`) addresses a stored key exactly, and it removes only a record that cannot be read (AGENTS.md "Route paths must round-trip"). Legacy keys that pass the schema but are not in normalised form (`/Promo`, `/promo/`) are the same: ordinary writes normalise them to another key, so a readable one still cannot be managed through them (an update or toggle of a listed `/Promo` still addresses `/promo`: an edit sending the row's `expectedUpdatedAt` is normally refused with 409, but a toggle, which sends none, changes the live `/promo`), but since v1.41.2 a delete never reaches another route (a non-normalised path with a record at its exact key, readable or not, is refused with 409 `ROUTE_KEY_NOT_NORMALIZED`). An exact-key mode for ordinary writes would let such a route be edited or removed; until then it needs the KV console (or `normalize-case`, for a capitalised path whose lower-case key is free).
- **Two keyed-TTL stores.** `admin/src/lib/route-pending.ts` and `admin/src/lib/qr-pending.ts` each carry their own keyed store with a TTL, an expiry timer, a `useSyncExternalStore` snapshot and expiry listeners. Extract one keyed-TTL store primitive (entries per key, expiry batches that drop only after their refetch settles, subscriptions) and build both on it, so a fix to one (such as v1.41.1's coalesced, refetch-gated expiry) reaches the other.
- **A delayed create row after a stale-read QR delete is live.** A QR create's D1 row is written after its answer (`afterAnswer`, `waitUntil`), so it can land after a later delete's write. The delete inserts deleted only the incarnation its own KV read named; when that read was stale (an older incarnation), the late create row of the deleted incarnation is inserted live, and a KV location still serving the deleted code lists it for up to the KV convergence window (about a minute). Likewise the delete's `UPDATE` marks deleted a code re-created between the delete's KV delete and its D1 write (even within the 1 s bound), which then shows once KV's own listing has it. And a delete whose D1 write outlasts its 1 s bound (`QR_RECENT_DELETE_TIMEOUT_MS`) lands after the answer: until it does, or KV converges, a listing at a KV location still serving the deleted code can merge it. Awaiting the create's write too (bounded, as the delete's) would close the first.
- **Migration 0013's header still describes the v1.41.0 rules.** `drizzle/0013_qr_recent.sql` says a delete sets `deleted` on its own incarnation's row and that an unreadable record is merged as its minimal row; since v1.41.1 a delete marks every recorded incarnation and an unreadable read is never merged (`src/db/qr-recent.ts` is current). The table is unchanged, and an applied migration file was left as it shipped; correct the comment if the file is next edited.
